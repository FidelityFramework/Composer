# eBPF and RA6M5 scaffold assessment — September 9, 2026

**Implementation follow-through:** the selected HelloBlinky path now runs on the physical RA6M5, including the user's requested 10% dimming. [The application acceptance record](../../MCU/Renesas/EK-RA6M5/HelloBlinky/docs/ACCEPTANCE.md) owns current evidence. The survey below records the pre-implementation decision and its original uncertainties; it is not a current missing-feature inventory.

**Recommendation: choose the narrowly scoped RA6M5 blinky/vector milestone if spending capacity this week; defer eBPF and actor/supervisor integration.** Keeping the remaining capacity is also reasonable because neither project is urgent. Attempting both offers poor odds of finishing a useful compiler-to-target path.

The final board candidate is: one of the EK-RA6M5's three colored user LEDs blinks; one user button cycles the active LED; the other cycles a small fixed set of blink rates. Reset, a periodic core exception, and two button interrupts exercise the vector path. This assessment concerns that milestone, not the full MMIO library, entropy pipeline, or conforming freestanding Ariel implementation.

“One third remaining” does not identify an absolute token or work budget. The rankings below are relative engineering estimates from source inspection, existing acceptance records, and small LLVM experiments; they are not measured implementation costs.

| Candidate | Smallest useful outcome | Fit for the remaining capacity | Main uncertainty |
|---|---|---|---|
| RA6M5 blinky with two buttons | Clef payload in a resettable ELF; timer and external vectors run; observable color/rate changes | Best bounded implementation candidate; moderate confidence | MMIO emission, target configuration, handler retention, and first board execution |

| Neither | Preserve capacity and start with a fresh budget next week | Entirely reasonable | No urgent dependency is being delayed |

The decision changes materially with scope. Full MMIO plus credential firmware is larger than a small eBPF experiment. Reset/vector bring-up with three LEDs and two buttons is a finite board exercise, and is the more attainable candidate for the present decision.

The narrow application scope does not reduce the intended platform scope. The EK-RA6M5 `Fidelity.Platform` package should grow into a comprehensive board description like ArtyA7, supporting subsequent RA6 projects. HelloBlinky consumes and validates its first subset. Renesas documents are already staged locally; the board package's source manifest now records the reviewed document revisions and hashes, with the initial hardware contract in `docs/HELLOBLINKY_HARDWARE.md`; complete board coverage remains work. Completing the entire board description is a separate work package from this week's proposed bring-up slice.

The survey included the [eBPF blog](../../clef-lang-site/hugo/content/blog/building-bulletproof-ebpf-programs.md), its [flight-bytecode companion](../../clef-lang-site/hugo/content/blog/flight-qualified-bytecode.md), the [Composer eBPF series](ebpf-targeting/README.md), the language specification, the [MMIO build guide](../../post-quantum-credential/hardware/ek-ra6m5/docs/MMIO-BUILD-GUIDE.md), [unikernel lowering specification](../../post-quantum-credential/hardware/ek-ra6m5/docs/UNIKERNEL-LOWERING-SPEC.md), and the board bring-up/triage materials. The [scheduler contract](../../clef-lang-spec/spec/scheduler-contract.md), [Ariel design](../../clef-lang-site/hugo/content/docs/design/concurrency/ariel-under-prospero.md), and current native acceptance record were also considered.

Several older planning assumptions need updating before estimating either task:

- CCS now has obligation elaboration/discharge and Composer reads those obligations for build-time work. The older M33 audit's claim that this machinery is absent is stale. This is reusable infrastructure, not evidence that BPF-specific admission obligations are implemented.
- BAREWire already contains host endpoint availability, BPF descriptor fixtures, and a struct-layout BTF serializer. The original eBPF proposal overstates what must be created from scratch. Wiring those declarations to compiler uses and a complete loadable artifact remains work; struct BTF alone is not a complete CO-RE or function-metadata pipeline.
- Composer's current LLVM tail uses `opt` and `ld.lld`, with explicit startup objects and linker scripts. Instructions assuming the older clang-driven native link should be revised. BPF needs a relocatable-object exit rather than the existing executable-link exit.
- At the survey baseline, source had no `Mmio` intrinsic-module case or dedicated MMIO witness, and no BPF target/root path. Merely selecting another LLVM triple does not supply either missing language contract.
- Hosted Ariel carriers now have [native acceptance evidence](Ariel_Integration_Changes.md). The older scheduler specification's blanket implementation-status statement should be read against that newer evidence. Hosted carrier progress does not establish the freestanding scheduler's timer, watchdog, supervision, or admission guarantees.

**The RA6M5 slice.** The normative [backend contract](../../clef-lang-spec/spec/backend-lowering-architecture.md) carries a typed MMIO operation until target serialization. The first implementation should recognize sanctioned register operations in CCS, retain access width and effects, and serialize the appropriate volatile LLVM operations. Address construction stays inside the register boundary. Ordinary `memref.store` is not sufficient evidence of MMIO semantics.

The narrow path can avoid generalized region inference, SVD ingestion, closure-based driver capabilities, dynamic allocation, ADC/DTC, USB, PQC, secure credential storage, and actor scheduling. Populate only the board facts needed for LED pins, button pins/IRQ routing, and the selected clock/timer configuration. Reuse the existing 32-bit MCU descriptor and native link facilities, while verifying the target actually receives Cortex-M33/Thumb and consistent ABI attributes.

Proposed acceptance sequence:

1. A fresh ELF has the correct initial stack/reset vectors, retained default fault handlers, initialized `.data`/`.bss`, and no unintended hosted runtime dependencies. A debugger can stop at reset and at the Clef entry. A reset or power cycle reaches the same entry without debugger initialization substituting for startup.
2. Exact-width register reads/writes survive the chosen optimization pipeline. A discarded read remains a load, and a polling load remains inside its loop. Inspect both LLVM IR and target disassembly; an individual machine load/store has no visible “volatile” marker. LLVM's [volatile rules](https://llvm.org/docs/LangRef.html#volatile-memory-accesses) preserve volatile access count/order, but do not provide general synchronization with ordinary memory.
3. A periodic SysTick exception drives a fixed tick. The app derives a visible blink cadence from it. This validates a core exception vector; it does not yet validate Renesas external interrupt routing.
4. Each button reaches its own configured external interrupt route. Button A cycles which colored LED is active; button B cycles, for example, 125/250/500/1000 ms half-periods. Keep SysTick fixed. Use short handlers and bounded debounce, with an explicit interrupt/mainline state-sharing discipline. Holding a button must not flood state changes or starve the timer.

Use the reset clock where practical, rather than adding a high-speed PLL sequence solely for blinking. Confirm the board's actual security state and the corresponding vector/register bank; these matter even though TrustZone policy and secure boot are outside this milestone. Do not inherit FreeRTOS exception handlers into the standalone image.

This is a useful precursor to Ariel: reset, timer delivery, external interrupts, fault visibility, and the download loop are all reusable. It does not yet demonstrate fair dispatch or supervisor recovery. A later freestanding Ariel milestone also needs the scheduler contract's control-plane resources armed before the first turn, bounded admission, lifecycle handling, and appropriate conformance evidence. The simulated scheduler profile can establish much of that independently of board debugging.

**The installed toolchain reduces uncertainty.** I found e² studio under `~/.local/share/renesas/e2_studio`, Arm GNU 13.2.Rel1, FSP 6.5.0 packs, and a SEGGER J-Link pack. More usefully, `~/e2_studio/workspace/card_flat` contains generated RA6M5 startup/pin/vector sources, a FreeRTOS blinky project, a built ELF, and an SWD launch configuration for `R7FA6M5AH`. These are concrete reference material and a candidate vendor baseline; their presence does not establish that the board was successfully programmed or is connected now.

The board provides an [on-board J-Link debugger/programmer, three colored LEDs, and two user buttons](https://www.renesas.com/en/design-resources/boards-kits/ek-ra6m5). Retain the Renesas environment as the reference and debug/download path while Composer supplies the payload. A later command-line download can use [J-Link Commander's ELF support](https://kb.segger.com/J-Link_Commander). A standalone Commander executable was not confirmed in PATH. Building a new flashing frontend is unnecessary for the first milestone.

**The eBPF slice.** Its strategic value is real: it would give the proof/lowering pipeline an independent admission check on its final artifact. The blog correctly separates source-level safety from bytecode shapes the verifier can recognize. The [kernel verifier](https://docs.kernel.org/bpf/verifier.html) tracks initialized state, pointer kinds, ranges, bounds and alignment; a linear stack sum or range proof alone does not reproduce that analysis. LLVM transformations, register spills, and host capabilities also matter. The supported subset and exact host/toolchain profile must be recorded, and an unresolved proof must not become an admission claim.

For a later first increment, use one Linux XDP profile: an initial pass-through object to establish artifact plumbing, then a guarded classifier or a per-CPU counter with positive and negative source cases. A constant `XDP_PASS` object proves little about pre-validation. A guarded packet access and a map lookup with a required null check supply more meaningful obligations. Save compiler diagnostics, object hashes, and kernel verifier logs together. The kernel's [program-run API](https://docs.kernel.org/bpf/bpf_prog_run.html) allows controlled execution tests without beginning with production interface attachment.

Defer a complete helper matrix, CO-RE, Windows/PREVAIL integration, general loops, AF_XDP, and ThreeBody integration. The [ThreeBody progression](ebpf-targeting/05_threebody_integration.md) already makes its rebuild a later synthesis. BPF will support transport and observation; admission does not prove numerical accuracy or payload preservation.

The machine has LLVM 22.1.8 with ARM and BPF targets, bpftool 7.8.0/libbpf 1.8, and cvc5. This shell has no effective capabilities and unprivileged BPF is disabled, so kernel admission testing needs a suitably privileged harness or test VM. No kernel program was loaded during this survey.

Two temporary LLVM-only probes confirmed that the installed backend emits Cortex-M33 Thumb code with a volatile store and unused readback, and a BPF ELF containing an XDP pass-through function. These bypass CCS/Composer and therefore establish backend availability only. No source-to-board or source-to-kernel path was claimed, and no device was flashed.

For capacity control, give the board work a short initial gate: establish target configuration, one typed MMIO operation through Composer, and a retainable handler/vector boundary before expanding to the buttons. If that exposes a broad compiler repair, stop at a documented reproducer and defer the implementation. Reserve a substantial part of the remainder for real board execution and reset tests. The two buttons are small additions after those foundations; the foundations are where the uncertainty sits.
